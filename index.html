Tutorial & Architectural Guide

ScanRest: Declarative API Testing for Spring Boot

ScanRest scans your Spring controllers, generates YAML test specifications, and executes them as first-class JUnit 5 tests — no hand-written test methods required. This guide covers the architecture, patterns, and every feature of the library.

Java 21 Spring Boot 4.1 JUnit 5 RestAssured YAML-driven
Chapter 1

Overview

ScanRest is an automated API testing library built for Spring Boot applications. The core idea: your controllers already declare their endpoints through annotations — ScanRest reads those declarations, builds a test plan from a YAML file, and runs it.

The library operates in three modes. LIVE sends real HTTP requests via RestAssured to a running server. MOCKMVC uses Spring's MockMvc to test controllers in-process, with full support for mocked services. EMBEDDED boots its own Spring context for standalone execution.

Tests are defined declaratively in YAML — from one-liners like GET /api/users: 200 to full specifications with headers, bodies, JSONPath assertions, schema validation, and test chaining. ScanRest converts each YAML entry into a JUnit 5 DynamicTest, so every test case appears individually in your IDE and CI reports.

Key Benefit You define what to test in YAML. ScanRest handles how to execute, assert, and report. When your API evolves, you update the YAML — not dozens of test classes.
Chapter 2

Quick Start

Add the dependency

<dependency>
  <groupId>io.scanrest</groupId>
  <artifactId>scanrest</artifactId>
  <version>1.0-SNAPSHOT</version>
  <scope>test</scope>
</dependency>

Enable ScanRest in your test

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@EnableScanRest
class ApiTests {

    @Autowired
    private ScanRestTestRunner runner;

    @TestFactory
    Collection<DynamicTest> apiTests() {
        return runner.toDynamicTests();
    }
}

Write your YAML test file

Place a file at src/test/resources/auto-tests.yml:

# Simple format — one line per test
tests:
  - GET /api/users: 200
  - GET /api/users/999: 404

  # Detailed format — full control
  - name: "Create a user"
    method: POST
    path: /api/users
    request:
      body:
        name: "Alice"
        email: "alice@test.com"
    expect:
      status: 201
      body:
        $.name: "Alice"
        $.id: NOT_NULL
  1. Add the Maven dependency to your Spring Boot project's pom.xml with test scope.
  2. Annotate your test class with @EnableScanRest and inject ScanRestTestRunner.
  3. Create a YAML file describing your API tests — use simple format for quick checks, detailed format for complex scenarios.
  4. Run with Maven or your IDE. Each YAML entry becomes a separate JUnit test in the results.
Chapter 3

System Architecture

ScanRest is organized into five subsystems: the Scanner discovers endpoints, the Generator produces YAML skeletons, the Parser reads YAML into test models, the Engine executes tests and evaluates assertions, and the Reporter formats results. The Spring auto-configuration layer wires these together.

Chapter 4

Design Patterns

Strategy Pattern — Execution Modes

The HttpExecutor interface defines a single contract: execute a request and return a response. Three implementations — LiveHttpExecutor, MockMvcExecutor, and EmbeddedSpringExecutor — encapsulate entirely different execution strategies behind the same interface. The TestRunner selects the strategy based on configuration, and the rest of the pipeline is unaware of which one is running.

Template Method — Test Lifecycle

The ScanRestTestRunner defines the test lifecycle as a fixed sequence: resolve variables, execute request, run assertions, save response values, and report results. Each step delegates to a specialized component. Subclasses or configuration do not alter the sequence, only the strategy behind each step.

Builder Pattern — YAML Parsing

The YamlParser reads both simple and detailed formats into a unified TestCase model. Simple entries are expanded into the same internal representation as detailed ones — the engine never sees format differences. This normalizes the two YAML dialects into a single object graph.

Observer — Spring Event Integration

When scanrest.run-on-startup=true, the runner listens for Spring's ApplicationReadyEvent and executes all tests automatically. This decouples test execution from the test framework — tests can run as part of application startup without JUnit involvement.

Chapter 6

YAML Test Specification

ScanRest supports two YAML formats in the same file. Use them interchangeably depending on how much control you need.

Simple Format

One-line test definitions for straightforward status code checks:

tests:
  # Just check the status code
  - GET /api/users: 200
  - DELETE /api/users/1: 204

  # Inline body assertions
  - GET /api/users/1: { expect: 200, body: { $.name: NOT_NULL } }

Detailed Format

Full test specification with all available fields:

- name: "Create user"
  method: POST
  path: /api/users
  request:
    headers:
      Content-Type: application/json
      Authorization: "Bearer {{token}}"
    queryParams:
      notify: true
    body:
      name: "Alice"
      email: "alice@test.com"
  expect:
    status: 201
    body:
      $.id: NOT_NULL
      $.name: "Alice"
    headers:
      Location: STARTS_WITH("/api/users/")
    schema: schemas/user.json
    save:
      userId: $.id
  auth: NONE          # omit Authorization header
  dependsOn: "Setup DB"  # skip if dependency failed

Config Block

Global settings at the top of the YAML file:

config:
  baseUrl: http://localhost:8080
  activeProfile: dev
  variables:
    token: "eyJhbGci..."
  profiles:
    dev:
      baseUrl: http://localhost:8080
      token: "dev-token"
    staging:
      baseUrl: https://staging.api.com
      token: "staging-token"

Use these in place of literal values in body or header assertions:

Example with Matchers

expect:
  status: 200
  body:
    $.id:       NOT_NULL
    $.name:     STARTS_WITH("Alice")
    $.email:    MATCHES("^[\\w.]+@[\\w.]+$")
    $.age:      GTE(18)
    $.tags:     SIZE(3)
    $.bio:      NOT_EMPTY
  headers:
    Content-Type: CONTAINS("json")
Chapter 9

Test Chaining

Tests can depend on each other and pass data forward. The save field extracts values from a response via JSONPath and stores them as variables. The dependsOn field references a previous test by name — if the dependency failed, the dependent test is skipped.

tests:
  - name: "Create User"
    method: POST
    path: /api/users
    request:
      body: { name: "Alice", email: "alice@test.com" }
    expect:
      status: 201
      save:
        userId: $.id

  - name: "Get User"
    method: GET
    path: /api/users/{{userId}}
    dependsOn: "Create User"
    expect:
      status: 200
      body:
        $.name: "Alice"

Profiles & Variables

Variables use the {{name}} syntax and are resolved from three sources in priority order: saved response values (highest), profile-specific variables, and global variables (lowest).

Defining Profiles

config:
  activeProfile: dev
  variables:
    defaultPageSize: 20
  profiles:
    dev:
      baseUrl: http://localhost:8080
      token: "dev-jwt-token"
    staging:
      baseUrl: https://staging.api.example.com
      token: "staging-jwt-token"
    prod:
      baseUrl: https://api.example.com
      token: "prod-read-only-token"

Chapter 11

Parameterized Tests

A single test definition can include a parameterized list. Each entry creates a separate test execution with its own variables and expected outcomes — useful for testing the same endpoint with many different inputs without duplicating the test definition.

How It Works

When ScanRest encounters a test with a parameterized field, it expands it into multiple JUnit 5 DynamicTest instances. Each entry in the list becomes its own named test:

# In the YAML, you write ONE test definition:
- name: "Test multiple user lookups"
  path: /api/users/{{id}}
  method: GET
  parameterized:
    - { id: "1",   expect: 200 }
    - { id: "2",   expect: 200 }
    - { id: "999", expect: 404 }
    - { id: "abc", expect: 400 }

ScanRest generates four individual JUnit tests from this single definition:

# JUnit test runner output:
Test multiple user lookups [1] {id=1, expect=200}     ✓ PASS
Test multiple user lookups [2] {id=2, expect=200}     ✓ PASS
Test multiple user lookups [3] {id=999, expect=404}   ✓ PASS
Test multiple user lookups [4] {id=abc, expect=400}   ✓ PASS

Anatomy of a Parameterized Entry

Each entry in the parameterized list is a map with two kinds of keys:

Key TypePurposeExample
Variable keysInjected into {{variable}} placeholders in path, body, headers, and query paramsid: "1", email: "alice@test.com"
expectOverrides the test’s default expect.status for this specific data setexpect: 200 or expect: { status: 404 }

Example 1: Path Variable Testing

Test the same endpoint with different IDs and verify each returns the correct status:

- name: "User lookup by ID"
  path: /api/users/{{id}}
  method: GET
  parameterized:
    - { id: "1",     expect: 200 }   # existing user
    - { id: "2",     expect: 200 }   # existing user
    - { id: "999",   expect: 404 }   # does not exist
    - { id: "abc",   expect: 400 }   # invalid format
    - { id: "-1",    expect: 400 }   # negative ID

Example 2: Request Body Validation

Test input validation by varying the request body fields across multiple data sets:

- name: "Create user validation"
  method: POST
  path: /api/users
  request:
    body:
      name: "{{name}}"
      email: "{{email}}"
      age: "{{age}}"
  parameterized:
    # Valid cases
    - { name: "Alice",  email: "alice@test.com",  age: "25",  expect: 201 }
    - { name: "Bob",    email: "bob@test.com",    age: "30",  expect: 201 }

    # Invalid email
    - { name: "Charlie", email: "not-an-email",  age: "22",  expect: 400 }
    - { name: "Diana",   email: "",              age: "28",  expect: 400 }

    # Missing name
    - { name: "",        email: "valid@test.com", age: "20",  expect: 400 }

    # Invalid age
    - { name: "Eve",     email: "eve@test.com",   age: "-5",  expect: 400 }
    - { name: "Frank",   email: "frank@test.com", age: "200", expect: 400 }

Example 3: Query Parameter Variation

Test pagination and filtering with different query parameter combinations:

- name: "Search users with filters"
  method: GET
  path: /api/users
  request:
    queryParams:
      page: "{{page}}"
      size: "{{size}}"
      sort: "{{sort}}"
  parameterized:
    - { page: "0", size: "10",  sort: "name,asc",  expect: 200 }
    - { page: "0", size: "100", sort: "name,desc", expect: 200 }
    - { page: "0", size: "0",   sort: "name,asc",  expect: 400 }  # invalid size
    - { page: "-1", size: "10", sort: "name,asc",  expect: 400 }  # negative page

Example 4: Chaining with Parameterized Tests

Parameterized tests can use saved variables from prior tests via {{variable}} syntax. The expect key can also be a map for richer assertions:

tests:
  # First, create a user and save the ID
  - name: "Create test user"
    method: POST
    path: /api/users
    request:
      body:
        name: "TestUser"
        email: "test@example.com"
    expect:
      status: 201
      save:
        userId: $.id

  # Then, test updating with various invalid payloads
  - name: "Update user validation"
    method: PUT
    path: /api/users/{{userId}}
    dependsOn: "Create test user"
    request:
      body:
        name: "{{newName}}"
        email: "{{newEmail}}"
    parameterized:
      - { newName: "Updated",  newEmail: "updated@test.com",  expect: 200 }
      - { newName: "",         newEmail: "valid@test.com",    expect: 400 }
      - { newName: "Valid",    newEmail: "bad-email",        expect: 400 }

Under the Hood

Internally, ScanRestTestRunner processes each parameterized entry as follows:

  1. Snapshot the variable store — calls VariableResolver.copy() to create an isolated copy of all current variables (globals, profile vars, and any saved response values from prior tests).
  2. Inject parameter variables — each key in the entry (except expect) is set on the snapshot resolver via paramResolver.set(key, value).
  3. Override expectations — if the entry contains expect, it overrides the test’s default expect.status. Can be an integer (expect: 200) or a map (expect: { status: 404 }).
  4. Execute and name — the test runs with the snapshot resolver and appears in JUnit as "Test name [index] {params}", e.g., "User lookup [3] {id=999, expect=404}".
Isolation guarantee Each parameterized run gets its own VariableResolver copy. If test [1] modifies a variable during execution, test [2] still sees the original values. This prevents data leaks between data sets.
When to use parameterized tests Use them for boundary testing (valid/invalid inputs), status code verification across multiple IDs, input validation (email formats, required fields, numeric ranges), and pagination/filter testing. Avoid them when tests need different request bodies or headers that can’t be captured with simple variable substitution — write separate detailed tests instead.
Chapter 12

Auto-Mock Services

When scanrest.mock-services=true, ScanRest replaces all @Service beans with Mockito mocks at startup. This lets you test controller routing, validation, and serialization without implementing any service logic.

# application.properties
scanrest.mode=MOCKMVC
scanrest.mock-services=true

The ScanRestMockConfiguration uses a BeanFactoryPostProcessor to intercept bean definitions. Every bean whose class is annotated with @Service is replaced with a Mockito mock via reflection. Requires spring-boot-starter-test (which includes Mockito) on the classpath.

When to use Auto-mocking is ideal for smoke-testing controller layers in CI — verify that endpoints are wired correctly and return the right HTTP status codes, without standing up databases or external services.
Chapter 13

CLI Reference

ScanRest ships as a fat JAR with three Picocli subcommands. Use the CLI to scan endpoints, generate YAML, and run tests outside of JUnit.

Commands

CommandDescriptionExample
scan Scans a classpath for Spring endpoints and prints them java -jar scanrest.jar scan --classpath target/classes
generate Scans endpoints and writes a skeleton YAML file java -jar scanrest.jar generate --classpath target/classes -o tests.yml
test Executes tests from a YAML file java -jar scanrest.jar test -f tests.yml --profile staging

CLI Workflow

# Step 1: Build your Spring Boot project
mvn compile

# Step 2: Generate a test skeleton
java -jar scanrest.jar generate \
  --classpath target/classes \
  -o src/test/resources/auto-tests.yml

# Step 3: Edit the generated YAML — add assertions, bodies, etc.

# Step 4: Run tests against a live server
java -jar scanrest.jar test \
  -f src/test/resources/auto-tests.yml \
  --base-url http://localhost:8080 \
  --profile dev
Chapter 14

Testing Strategies

ScanRest supports seven distinct strategies, each suited to different testing goals. Choose based on what you need to verify and how much of the stack you want running.

StrategyModeSpring ContextUse Case
A: Full Integration LIVE @SpringBootTest(RANDOM_PORT) End-to-end testing with real HTTP and full application stack
B: MockMvc + Mocks MOCKMVC @SpringBootTest + @MockBean Controller testing with developer-controlled service mocks
C: Controller Slice MOCKMVC @WebMvcTest(Controller.class) Lightweight — loads only the controller layer
D: Auto-Mock MOCKMVC scanrest.mock-services=true All services auto-mocked — verify wiring only
E: In-Memory DB LIVE @ActiveProfiles("test") + H2 Full stack with a disposable test database
F: Auto-run Any scanrest.run-on-startup=true Batch run on app startup, single JUnit result
G: Batch Any Manual runTests() call Single @Test wrapping all YAML tests
Recommendation Start with Strategy A (full integration) for confidence, then add Strategy C (controller slice) for fast feedback on controller logic during development. Use Strategy D (auto-mock) for CI smoke tests that verify endpoint wiring without external dependencies.
